# 系统声音低延迟

## 2026-11-17 修正：协议对照结果（覆盖下文旧策略）

对照WinPods固定提交5d6d291，修正两处源码问题：①实验模式不再因接收端省略latencyMin/latencyMax而静默退回2000ms，保留600ms请求目标并服从已返回的边界；②PTP D7报文的offset4直接写当前渲染位置，offset16写渲染位置加实际提前量，删除11035/77175固定偏移。原始实现和回环模拟器共享错误偏移假设，旧检查通过不能证明协议语义正确。本轮导入WinPods的11条独立D7报文向量（含RTP回绕、首包及2s模式），许可证与固定来源见THIRD-PARTY.md。

保持600ms以隔离协议修正的效果，不同时缩到100ms；现有100ms采集缓冲尚需后续缩短和稳定性验证。标准模式、原生对统一时间轴、已知范围交集、非法范围拒绝与时钟失效保护保留。缺项不等于设备批准较低缓冲，界面明确显示按实验目标发送、实际出声待验证。未取得用户诊断，不能断言此次约2s的唯一原因，也未完成真机降延迟验收。

## 目标与已撤销路线

Windows全部系统声音送到HomePod，保持桌面、鼠标与游戏实时操作。浏览器、指定播放器及整个桌面画面延后均已撤销；不能用音画一起变慢冒充游戏低延迟。曲目/封面/进度与组合发现修复继续保留。

## 本轮实现

原代码初始化发送端播放提前量为88200样本（44.1kHz下2000ms），先套接收端latencyMin再套latencyMax。该默认值来自发送端，不是已证明的HomePod最低延迟；原写法在最小值大于最大值时还可能落到最小值以下。

新增声音延迟设置：标准目标2000ms；较低缓冲实验目标600ms。600ms是本轮验证用的发送调度目标，不是测得的出声延迟，也不足以承诺游戏体验。保留原流SETUP声明的11025–88200样本能力范围，不伪造接收端能力、不改变媒体类型或添加镜像会话。

- 收到完整接收范围才尝试较低目标，选择值限制在接收范围及本实现250ms下限内；缺项保留2000ms目标并服从已知边界。字段类型错误、范围矛盾或越界直接停止准备。
- 原生对在发音频与组合音量确认前求范围交集，统一提前量；无交集停止，不能双成员各自选值后强行取大。
- 首包前固定时间轴，播放中拒绝修改。较低缓冲开启时使用既有ClockAligned与100ms采集率补偿缓冲；不放宽PTP、所有权或迟到保护，不自动降档重连。
- 分别报告请求目标、各成员返回范围、最终发送提前量、接收端arrivalToRenderLatencyMs（若有）及本机采集队列估算。声学结果始终标为未测；不把这些数字相加就宣称端到端测量。

## 使用与验证

### 用户初测反馈（2026-11-16）

用户在体验后用“点击音乐播放，同时按手机秒表”的方法估计出声延迟仍约2s，撤回此前“似乎有改善”的初步感觉。当前结论为低延迟目标尚未验证达成；该操作到出声估计包含手动操作误差、播放器启动与音源起始静音，不能当作精确传输延迟，也不能据此断言HomePod的硬件最低延迟。此次会话是否启用较低缓冲并重连、实际选择的发送提前量与接收端范围尚未取得诊断证据。

下一步先取得保持连接时导出的诊断，核对PreferReducedLatency、SenderLeadFrames、AudioLatencyReports（含Decision及接收范围）与CaptureLagEstimateMs：区分未启用/缺项保留标准目标/接收范围抬高目标，及已经降低发送提前量但实际出声仍慢。未定位前不盲目继续缩小目标数字，不将600ms实验目标写成实际延迟。

设置 → 声音延迟 → 较低缓冲（实验）。默认关闭；先断开连接再修改并重新连接；开关会保存。它作用于系统混音，不需要扩展或从WinToPod启动播放器。卡顿或无声时关闭后手动重连。旧配对、音量、自动连接偏好保留。

同一音源分别记录标准/实验两轮：接收端范围、实际选择、采集队列；用另一台设备高帧率录制屏幕闪光与HomePod短音，比较两者时间差。此方法测的是该音源的音画偏差，并包含显示/录制误差，不等于独立的按键到出声延迟。游戏须另录实际按键/动作反馈到出声，并分别测试单只与原生对。没有真机结果前不承诺低于某个毫秒值。

当前可自动检查范围边界、缺项、组合交集、真实同步报文、短缓冲迟到停止，以及双模拟接收端完整鉴权/协商/同锚推流。它们不能替代HomePod实际缓冲是否服从调度、音质、网络波动或游戏体验。构建与结果见V1.2-PROGRESS.md顶部。

## 协议参考与推断边界

### 现成实现补查（2026-11-16）

- TuneBlade官网文档本次访问超时；其[官方支持答复](https://groups.google.com/g/breakfreeaudio/c/eQGQFsJvAlQ)确认实时/自定义缓冲可受接收端最小缓冲约束，并曾为TuneAero提供140ms默认下限的覆盖方式。此为软件接收端案例，不能套用为HomePod实测。另一次[官方答复](https://groups.google.com/g/breakfreeaudio/c/Mc1yNbe-kso)确认VLC音画偏移会考虑系统延迟与缓冲；音频低缓冲与播放器同步是不同机制。尚未取得TuneBlade内部源码或抓包，不能宣称已还原其具体协议实现。
- [WinPods](https://github.com/sheepy928/WinPods)文档称已在HomePod mini/tvOS 27测试，提供100ms档及75ms自定义下限，并说明PTP、接收端arrivalToRenderLatencyMs、同步时间轴与重采样控制。数字为作者说明/设置，尚未由本项目声学验证；原生立体声组适用性待核实。
- [HomePodCast](https://github.com/qiyinxi/HomePodCast)文档列出HomePod实时PCM、120ms默认及105ms游戏档，实际硬件验证范围列为一只HomePod 2；明确接收端可能忽略延迟请求。不能把单只结果推广到用户mini原生对。
- [AirPlay Bridge](https://github.com/RiverFlowsInUUU/airplay-bridge)提供100–300ms设置，作者将250ms列为已测试折中值、130ms标为实验；可作为额外协议实现参考。

这些项目使低延迟音频链路有了更直接的对照对象，但README参数不构成本项目的端到端实测证据。接下来优先比较实际SETUP字段语义、RTP/Sync时间映射、接收渲染处理时间与采集积压，再结合用户诊断定位当前约2s。现有策略把latencyMin/latencyMax当作硬边界并在缺项时保留2000ms，这一解释本身也需要用实现和设备行为验证，不能循环引用自身模拟器证明其正确。用户已取消的浏览器、播放器和桌面画面延后不恢复。

公开发送端[Music Assistant airplay-cli设计](https://github.com/music-assistant/airplay-cli/blob/main/DESIGN.md)描述了realtime type96、接收窗口及arrivalToRenderLatencyMs；[接口声明](https://github.com/music-assistant/airplay-cli/blob/main/src/ap2_client.h)区分有效提前量与设备报告范围。参考读取日期2026-11-15；本项目自行实现策略，没有复制该项目代码，也不把其他发送端或设备表现当成本机HomePod验证。

下一步以同包标准/实验实测判断主要限制：若设备不报告范围，保持标准值并根据诊断继续验证可用协议；若降低发送提前量但实测不变，检查接收端渲染缓冲与实际Sync映射。不得再次把显示延后、内容类型伪装或一味减少数字作为完成标志。
